## ۱. خواندن از انبار + اثبات بایت‌به‌بایت

قبلاً هر بار ساخت ماتریس، هر ۱۰۹ ویژگی از نو حساب می‌شد — حتی وقتی
`Update features` همان اعداد را چند ثانیه قبل روی دیسک نوشته بود.

حالا `build_feature_matrix` یک پارامتر `source` دارد. تنها چیزی که عوض
می‌شود **از کجا** ستون‌ها می‌آیند است؛ مقیاس‌بندی نسبت به close، برش
warm-up و برش tail همه در یک جا می‌مانند و بین دو مسیر مشترک‌اند. دقیقاً
همین است که اجازه می‌دهد ادعای «یکسان» تست‌پذیر باشد.

### اثبات روی دیتای واقعی ۱ ساعته

```
real 1H candles: 3000  2026-02-12 .. 2026-08-17
computed: 2897 x 123   in 3.31s
loaded  : 2897 x 123   in 1.59s   (2.1x faster)
columns identical : True
source_index same : True
warmup same       : True
BYTES identical   : True   (2,850,648 bytes each)
```

تست‌ها این را برای **هر سه تایم‌فریم** (5M/1H/1D) با `struct.pack("<d")`
مقایسه می‌کنند.

### یک باگ که سر راه پیدا شد

انبار `warmup` را ذخیره نمی‌کرد. `warmup` مقدار نیست — تعداد سطرهای ابتدایی
است که مقدار صادقانه ندارند — و `build_feature_matrix` با آن تصمیم می‌گیرد
ماتریس از کجا شروع شود. اگر ذخیره نمی‌شد، ماتریسِ خوانده‌شده **بی‌صدا** با
محاسبه‌شده فرق می‌کرد. حالا در metadata پارکت می‌نشیند و تست
`test_the_warmup_survives_the_round_trip` نگهش می‌دارد.

### سه محافظ

| خطر | رفتار |
|---|---|
| دیتاست عوض شده | اثر انگشت فاز ۳۸ → `None` → محاسبهٔ کامل |
| طول نامساوی | آن ویژگی رد می‌شود، با ذکر دلیل |
| **timestamp جابه‌جا** | رد می‌شود — خطرناک‌ترین حالت: طول یکی، کندل‌ها متفاوت |
| کش ناقص | کل ماتریس دوباره حساب می‌شود، نه ستون کمتر |

## ۲. تایم‌فریم یک روزه — همه‌چیزِ ۱ ساعته، برای ۱ روزه

### کندل روزانه

بروکر معمولاً 1D می‌دهد، ولی تو سال‌ها 1H داری. پس یک resampler دامنه‌ای
اضافه شد و دکمهٔ **Build a higher timeframe** آن را از GUI اجرا می‌کند:

```
XAUUSD: 2,255 1D candles from 50,000 1H
  dropped : 2 incomplete bucket(s) (fewer than 24 source candles)
  continuity : OK — no gaps
  first day: 2017-11-16  O=1277.04 H=1281.74 L=1275.13 C=1278.61
  last  day: 2026-08-14  O=4353.11 H=4396.91 L=4311.09 C=4376.25
```

دو قاعده که نادیده‌گرفتنشان گران است:

1. **سطل ناقص دور ریخته می‌شود.** آخرین «روز» یک سری ساعتی تقریباً همیشه
   نصفه است؛ شش ساعت از بیست‌وچهار. high و low آن، high و low روز نیست و
   سطرش کاملاً عادی به‌نظر می‌رسد.
2. **گپ‌ها به هم جوش نمی‌خورند.** سطل‌بندی بر اساس تاریخ تقویمی UTC است نه
   شمارش، پس آخر هفته سطل تولید نمی‌کند و جمعه به دوشنبه نمی‌چسبد.

### ویژگی‌ها و دیتاست روزانه

```
1D: 109/109 recomputed over 2,255 candles
1D slice: 2152 rows x 123 cols
  warmup 77 | tail 26 | contiguous True
  columns = 14 candle + 109 catalogue
  source used : stored          ← از انبار خوانده شد
```

### مدل رنج روزانه — آموزش واقعی

هر تایم‌فریم **شناسهٔ مدل خودش** را دارد (`gold_range_1h` در برابر
`gold_range_1d`). اگر مشترک بود، آموزش دوم اولی را بازنویسی می‌کرد و
artifact store هرکدام را که آخر نوشته شده بود پس می‌داد، بدون هیچ راهی
برای تشخیص.

## ۳. انتخاب مدل و دیتاست

دکمهٔ آموزش سه فیلد جدید گرفت:

| فیلد | مقادیر |
|---|---|
| `Model` | `all` · `range_1h` · `range_1d` · `signal` · `range` · `both` |
| `Range dataset(s)` | `1H,1D` |
| `Signal dataset` | `5M` |

`range_1d` یعنی «مدل رنج روزانه را با کندل‌های 1D آموزش بده» — و روی 1H
آموزش نمی‌دهد. خروجی هم صریح می‌گوید کدام مدل با کدام دیتاست:

```
training: range(1D)
  model id : gold_range_1d
  dataset  : XAUUSD 1D
```

## ۴. چرا در پاورشل چیزی چاپ نمی‌شد — دو علت واقعی

این را روی دیتای واقعی بازتولید کردم: **۲۰۸ ثانیه، صفر خط خروجی.**

### باگ ۲۹ — ۲۴٬۹۷۶ فولد

`val_size=4, step=2` برای سری دموی چندصد سطری تنظیم شده بود. روی ۵۰٬۰۰۰
کندل واقعی:

```
folds for the real 1H series: 24,976
```

هر فولد یک fit کامل مدل است. این «کند» نیست — تمام نمی‌شود. حالا هندسهٔ
roll-forward با اندازهٔ دیتا مقیاس می‌گیرد:

```
val_size=999 step=999 min_train=640 -> folds=49
```

### باگ ۳۰ — ۱۰ ثانیه سکوت قبل از اولین خط

ساخت ۵۰٬۰۰۰ پنجرهٔ همپوشان ~۱۰ ثانیه طول می‌کشد و **قبل** از
`on_train_begin` اتفاق می‌افتاد. حالا اعلام می‌شود:

```
  preparing 49,995 rows into windows of 32 (this takes a moment) ...
  2,121 training windows ready in 2s
```

### و پیشرفت درون epoch

یک epoch روی ۵۰k نمونه هزاران batch است. حالا:

```
fold   1/2 | train[0:2000] (2000 samples) -> val[2000:2043] (43 samples)
    [#############-------]  66.8% | loss 0.0016 | mae 0.0260 | batch    501/750
  epoch 1/1 | loss 0.0018 | val_loss 0.0016 | lr 1.50e-04
[##############--------------]  50.0% | fold 1/2 | val_loss 0.0016 | eta 0s
```

خط batch در جا به‌روز می‌شود (`\r`) تا لاگ را غرق نکند.

**یک نکتهٔ سازگاری:** قرارداد reporter بزرگ‌تر شد. یک reporter قدیمی‌تر
هنوز معتبر است — فقط کمتر می‌بیند — پس hookهای غایب رد می‌شوند نه اینکه
خطا بدهند. مشاهده هرگز نباید آموزش را بشکند.

## ۶. آنچه هنوز باز است

- **مدل سیگنال 5M روی ۵۰k کندل هنوز کند است.** با ۴۹ فولد و ~۶٬۲۰۰ batch در
  هر epoch، یک اجرای کامل ساعت‌ها می‌برد. برای اجرای واقعی `--folds 2` یا
  batch بزرگ‌تر لازم است؛ اعداد پیش‌فرض هنوز برای دیتای این اندازه تنظیم
  نشده‌اند.
- **مدل رنج 1D فقط ۲٬۱۲۱ پنجره دارد** (۹ سال دیتای روزانه). این کم است و
  مدل زیر-برازش می‌کند؛ `val_mae 0.0162` یعنی ~۳۲ دلار خطا روی طلای ۲۰۰۰
  که برای معامله بزرگ است. صادقانه گزارش شده، پنهان نشده.
- **resampler فقط 1H→1D/4H را پوشش می‌دهد.** اگر بروکر مستقیم 1D بدهد،
  `Fetch market data` با `1D` در لیست بهتر است — دیتای اصل همیشه بر
  بازسازی ارجح است.

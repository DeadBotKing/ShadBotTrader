# فاز ۶۴ — باگ ۴۹: برش last_n رنج را گرسنه می‌کرد → trades=0

**تاریخ:** 2026-08-27 · **وضعیت:** ✅ فیکس (pytest 1478 passed · 49 skipped)
**کشف از:** اولین بکتست واقعی کاربر — dual engine، مدل‌های جدید سالم، trades=0

## ریشه‌یابی

`handlers._run_simulation` کندل‌های 1D را با همان cutoff زمانیِ پنجرهٔ
«last N bars» می‌برید:

```
۹٬۰۰۰ کندل 5M (تست سریع کاربر) ≈ ۳۱ روز
→ برش range با cutoff → فقط ~۳۰ کندل 1D می‌ماند
→ مدل رنج window=150 می‌خواهد → abstain همیشگی
→ هیچ RangeForecast تولید نمی‌شود → گیت «no range forecast» → trades=0
```

**چرا تشخیص دیر شد؟** گزارش بکتست تعداد کندل‌های 1D ورودی را چاپ نمی‌کرد —
فقط «replay bars: 9000». تراوش اطلاعات صفر بود.

**چرا فیکس = حذف برش؟** علیت را خود `DualModelPredictionSource`
enforce می‌کند: cursor فقط کندل‌های 1D **بسته‌شدهٔ قبل از زمان تصمیم** را
به پنجره می‌دهد. تاریخچهٔ کامل 1D هیچ نشتی ایجاد نمی‌کند؛ بریدنش فقط
context را می‌کُشت.

## رفع

1. برش range با cutoff حذف شد (+ هشدار اگر اصلاً کندل 1D نباشد).
2. گزارش بکتست حالا خط جدید دارد: `range candles: 5,698 (1D)` — کمبود
   خوراک رنج دیگر نامرئی نیست.
3. ۳ تست رگرسیون: `tests/unit/simulation/test_range_window_starvation.py`
   (سناریوی گرسنگی با ۳۰ کندل · خوراک کامل · قفلِ متنیِ handler).

## آنچه بعد از re-run انتظار داریم

- `range candles: 5698 (1D)` در گزارش
- سیگنال‌های ≥60% → forecast رنج → براکت R/R=1.0 (به‌خاطر spread، فقط
  سیگنال‌هایی که upside مدل به‌قدر کافی از downside بزرگ‌تر باشد براکت
  می‌گیرند) → trades > 0
- اگر باز trades=0 شد، قدم بعدی: قیفِ گیت‌ها (تعداد confidence-pass /
  bracket-reject) را به گزارش اضافه می‌کنیم — تصمیم را با عدد می‌گیریم نه حدس.

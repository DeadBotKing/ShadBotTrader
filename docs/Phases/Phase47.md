# فاز ۴۷ — بهترین مدل نگه داشته می‌شود، نه آخرین

**تاریخ:** 2026-08-18
**وضعیت:** ✅ کامل — Quality Gate سبز

---

## سؤال تو

> «مدلای آموزشی آخرین مدل آموزش دیده رو ذخیره میکنن یا بهترین مدلی ک
> آموزش دیده رو ذخیره میکنن؟»

**جواب صادقانه: آخرین.** و این یک ضعف واقعی بود.

```python
last_model = model                    # هر fold، بدون شرط
payload = _serialize_model(last_model)
```

## چرا این مهم است

خطای آموزش (`loss`) تقریباً همیشه کاهش می‌یابد. خطای اعتبارسنجی
(`val_loss`) این‌طور نیست: پایین می‌آید، به کف می‌رسد، بعد **بالا می‌رود**
چون شبکه شروع به حفظ‌کردن می‌کند.

پس ذخیرهٔ «هرچه آخر اجرا شد» یعنی ذخیرهٔ **بیش‌برازش‌شده‌ترین** وزن‌های آن
اجرا.

اندازه‌گیری واقعی روی دیتای تست:

```
epoch  1: val_loss 2.2031 | val_acc  9.1%
epoch  2: val_loss 0.9262 | val_acc 63.6%
epoch  3: val_loss 0.8477 | val_acc 81.8%
epoch  5: val_loss 0.8055 | val_acc 72.7%   ← بهترین
epoch  8: val_loss 0.9978 | val_acc 63.6%
epoch 12: val_loss 0.8969 | val_acc 63.6%   ← قبلاً این ذخیره می‌شد
```

**۹ واحد دقت، دور ریخته‌شده به‌خاطر یک انتساب متغیر.**

توجه کن `loss` آموزش از ۱.۰۲ به ۰.۲۸ رسید — عالی به‌نظر می‌آید — ولی
`val_loss` از epoch ۵ به بعد بدتر شد. مدل داشت دیتای آموزش را حفظ می‌کرد.

---

## رفع

### ۱. فقط وقتی بهتر شد ذخیره کن

```
[BEST so far] epoch 5/12 val_loss 0.805476 — saved as v1
[epoch 6/12] val_loss 0.894731 — no better than 0.805476 (best is epoch 5); keeping it
[epoch 7/12] val_loss 0.908194 — no better than 0.805476 (best is epoch 5); keeping it
```

هر epoch می‌گوید چه شد و چرا. سکوت نیست.

### ۲. چرا `val_loss` داور است نه `val_accuracy`؟

دقت روی مسئلهٔ سه‌کلاسه با پله‌های درشت حرکت می‌کند و مدام مساوی می‌شود
(در لاگ بالا سه بار پشت‌هم ۶۳.۶٪). `val_loss` هر بهبود کوچک در اطمینان
مدل را ثبت می‌کند. برای مدل رنج، `val_mae` جایگزینش می‌شود.

### ۳. ذخیرهٔ نهایی، بهترین را بازنویسی نمی‌کند

قبلاً `save_model()` در پایان یک نسخهٔ **جدید** از وزن‌های آخرین epoch
می‌نوشت. یعنی دو مدل روی دیسک می‌ماند و **بدتره** بالای منوی کرکره‌ای
می‌نشست. حالا:

```
KEPT   gold_signal_5m v1 from epoch 5 (val_loss 0.805476)
  the final epoch scored 0.896911 — worse, so it was NOT written over the best one
```

یک نسخه روی دیسک، از بهترین epoch:
```json
{"epochs": 5, "note": "best epoch 5/12 (val_loss 0.805476)"}
```

## دربارهٔ اجرای خودت

خبر خوب: در آن اجرای دو ساعته چیزی از دست ندادی.

```
epoch 17: val_loss 0.5314
epoch 18: val_loss 0.5279   ← هنوز در حال بهبود
```

هر دو در جهت درست، پس «آخرین» همان «بهترین» بود. ولی اگر تا epoch ۲۰
می‌رفت و از ۱۹ به بعد بدتر می‌شد، با کد قدیم مدل بدتر را نگه می‌داشتی.

## هر دو مدل، تأییدشده

سؤال بعدی تو این بود که آیا این کار برای **هر دو** نوع مدل انجام شده.
جواب: بله — هر دو از یک `train_one` استفاده می‌کنند. ولی «باید کار کند»
دلیل نیست، پس هر دو را با همان منحنی بیش‌برازش آزمودم:

```
SIGNAL: metric=val_loss  curve=[0.71, 0.55, 0.51, 0.53, 0.58, 0.64]
         best epoch = 3  |  SAVED epoch = 3  |  files=['v1.bin']
         note: best epoch 3/6 (val_loss 0.510000)          -> CORRECT

RANGE : metric=val_mae   curve=[0.031, 0.022, 0.018, 0.021, 0.027, 0.034]
         best epoch = 3  |  SAVED epoch = 3  |  files=['v1.bin']
         note: best epoch 3/6 (val_mae 0.018000)           -> CORRECT
```

هر دو epoch ۳ را نگه داشتند و ۴ تا ۶ را رد کردند.

**یک نقص جزئی که همین آزمون لو داد:** برچسب لاگ همیشه `val_loss` می‌گفت،
حتی برای مدل رنج که `val_mae` گزارش می‌کند. یک مدل رنج که «val_loss»
چاپ کند، اپراتور را دنبال عددی می‌فرستد که در لاگش وجود ندارد. رفع شد و
تست دارد.

## بدهی صریح

- **معیار انتخاب قابل تنظیم نیست.** همیشه `val_loss` (یا `val_mae`).
  اگر بخواهی بر اساس `val_accuracy` انتخاب شود، باید فیلد اضافه شود.
- **توقف زودهنگام (early stopping) نداریم.** اگر ۲۰ epoch بدهی، هر ۲۰
  اجرا می‌شود حتی اگر از epoch ۵ به بعد بدتر شود. بهترین مدل نگه داشته
  می‌شود ولی وقتش تلف می‌شود. اگر بخواهی، `patience` اضافه می‌کنم تا بعد
  از N اپاک بی‌بهبود خودش متوقف شود.
- **`val_loss` فقط روی آخرین fold سنجیده می‌شود.** با چند fold، هر fold
  مدل خودش را دارد و فعلاً آخرین fold برنده است.
